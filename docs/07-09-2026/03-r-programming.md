I got tired of search engines that return 0 and call it "no results" — so every answer of this one is verified against grep, on the whole Linux kernel

Every full-text engine I have used lies a little: two characters return nothing, a typo across an underscore finds nothing, a regex is "not supported on this field", and the highlight shows you the top 200 and stops. None of them tells you.

So the rule of this one is that **every answer is checked**. The test harness indexes the Linux kernel (93 983 files, 857 MB of text), runs a panel of queries, and compares every document count *and every byte span* to a byte-by-byte scan of the files. Any disagreement fails the build. Zero mismatches in the current release.

**One index, every question.** Exact substrings, matches across separators (`spin_lock` finds `spin lock`, `spin-lock`, `spinlock`), typos across token boundaries, regular expressions, two-character needles, boolean queries — with BM25 ranking and the exact position of every match. Nothing to configure per question: it is all an option at query time.

**Against Elasticsearch and tantivy on the same corpus**, each configured at its best for substring search (Elasticsearch with trigrams plus a `wildcard` field, tantivy with its n-gram tokenizer), the "truth" column being the scan:

| asked | truth (scan of the files) | lucivy 4.0 | Elasticsearch 8.19 | tantivy 0.25 |
|---|---|---|---|---|
| `spin_lock`, separators relaxed (`spin lock`, `spin-lock`, `spinlock`) | 9 552 | **9 552**, 23 ms | 6 577 | 6 601 |
| `spinlokc`, two edits, across the token boundary | 10 034 | **10 034**, 148 ms | 3 549 | 6 557 |
| `spin_lock_[a-z]+`, a regex | 5 510 | **5 510**, 219 ms | 5 440, 480 ms | 0 |
| `de`, two characters | 93 009 | **93 009**, 561 ms | 0, silently | 0, silently |
| `retur -ENOMEM`, a fuzzy phrase | 14 449 | **14 449**, 30 ms | 14 446, 24 ms | — |
| `mutex_lock`: where it matched, in 5 145 documents | 20 797 spans | **all 20 797, 15 ms** | top 200 only: 179 ms | 96 ms |

Where they win, because they do: tantivy indexes the corpus in 1-5 s against 107 s here, and its index is 7× smaller; Elasticsearch does the fuzzy phrase as well. The full report, sizes and configurations included, is generated by one script in the repo.

**The price.** Disk: the index is 5.8× the text (3.9× with an option), against 3.6× for Elasticsearch's trigram setup. What you get for it is an index that doesn't lie, and questions the other two cannot ask.

**Where it runs.** It is a library, not a server: Rust, with Python, Node.js and C++ bindings, MIT. It runs in your process, inside your database transaction if you plug your own storage, and the same engine runs in the browser — the demo below clones its own source from GitHub and indexes it in your tab in 3 s, then PostgreSQL's 5 199 files in 14 s, every search timed live. You can type your own.
